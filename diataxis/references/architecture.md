# Documentation site architecture

The four modes are the load-bearing structure. This file covers everything built on top:
the tree, landing pages, navigation, cross-linking discipline, the material that is not
practitioner documentation, and what to do when the doc set has a second dimension.

## The default tree

```
docs/
  index.md                  # site landing page
  start/                    # orientation, before the modes — see below
    what-it-does.md
    is-it-right.md
    quickstart.md
  tutorials/
    index.md                # section landing page
    first-pipeline.md
    ...
  how-to/
    index.md
    authenticate.md
    deploy-to-kubernetes.md
    ...
  reference/
    index.md
    cli.md
    configuration.md
    errors.md
    api/                    # generated
  explanation/
    index.md
    architecture.md
    why-immutable-configs.md
  about/                    # not practitioner docs — see below
    changelog.md
    contributing.md
```

Folder-per-mode is the default because it makes the mode a property of the path, which means
tooling can see it, contributors cannot accidentally file things wrong, and nav generation is
free. Flat trees with grouped nav entries work for small sites but lose all of that.

Create a folder when it has content — or, on a greenfield site where the tree *is* the
deliverable, when its landing page is fully written and names what is not yet there. What you
must never ship is a folder of confident-looking empty pages that nothing acknowledges: a reader
clicks Explanation, finds one stub, and stops trusting the nav.

## Before the modes: the `start/` doorway

All four modes serve a reader who has already decided to use the software. A reader still
deciding *whether* to is served by none of them: a tutorial asks for an hour of work before it
says what the thing is, reference answers questions they do not yet know they have, and
explanation discusses the design of a system they have not agreed to adopt. That reader lands on
`index.md`, sees four doors that all assume adoption, and leaves.

The fix is a small orientation section, at most three pages, placed first in the nav:

```
docs/
  index.md
  start/
    what-it-does.md
    is-it-right.md
    quickstart.md
  tutorials/
  how-to/
  reference/
  explanation/
  about/
```

**`what-it-does.md`** — the mental model, in the project's own terms: what problem the software
addresses, what it produces, and the shape of the thing you get back (what you hand it, what
comes out, what type that is). Prose, not a feature list; a reader should be able to decide from
this page alone whether to keep reading. It names the default path through the software in a
paragraph or two and links to explanation for the mechanism rather than describing it.

One figure earns its place on this page, when the product can produce one: a picture of the
problem and of the answer, generated by running the software with the code hidden, captioned
with the setup that produced it. A reader deciding whether any of this applies to them will look
at a figure when they would not read three paragraphs, and a generated figure rots with the
product instead of behind it.

**`is-it-right.md`** — the distinctive page, and the one with no possible home in the four modes,
because every mode presumes adoption. It answers "does this apply to my data, or my problem, at
all". It is built from triage tables that route rather than describe — one keyed on what the
reader has, one on what they want:

```
## What you have

| You have | Use | Read more |
|---|---|---|
| <a property of the reader's data or situation, in their words> | <the call, class or setting that handles it> | <the how-to or tutorial> |

## What you want

| You want | <Project> gives | Read more |
|---|---|---|
| <an outcome the reader came for> | <the attribute, call or result that is it> | <the page> |
```

Every row is a sentence the reader can recognise as their own case, and every row ends in a
link, so the page is a switchboard and never an explanation. One row is the exception: the case
the software does not serve, whose honest answer is "nothing here, use the standard library" and
which has nowhere to link. That row is worth more to a stranger than most of the others, so
write it and leave its last column empty.

Then two short lists, a few bullets each. **"What it does not do"** — the honest limits, each one
stated plainly. **"What it costs"** — the dependencies it adds, the global state it touches, the
work a reader takes on by adopting it. Together they are what make the page trustworthy, and no
mode will host either: reference describes what exists, explanation discusses why it was built
that way, and neither of them will tell a reader "this is not for you." Link the facts rather
than restating them. A cost that spells out a default or a registration rule is reference
material with a second copy here, and the second copy is the one that goes stale.

**`quickstart.md`** — the smallest end-to-end result: install, call, look at the output, stop.
Shorter than a tutorial and with no teaching ambition, so the tutorial preflight does not apply
to it — but its code must run, and its output must be real. It has one path and no branches; a
reader who wants to learn goes to the tutorial, which this page links to at the end.

**`principles.md`** — sometimes earned, for a project whose claim on a reader is the quality of
its answers rather than a list of features. It states what the software promises: what it
guarantees about its results, what one call does and what is exposed underneath it, which answers
are exact and which are labelled as approximations, what it checks on the reader's behalf, what
it costs to install. Numbered, one or two sentences each, and every item ends in a link to the
page that owns the fact, so the page is a list of commitments with a bibliography rather than a
second copy of the reference. An item that cannot be checked against the code as it stands is a
roadmap entry and does not belong on it. Most projects do not need this page: write it when the
adoption decision turns on the guarantees, and skip it when the honest version would restate
`what-it-does.md`.

**Installation is usually one line on the landing page or in the quickstart**, not a page. It
earns `start/install.md` only when there is a genuine choice to document: optional extras,
accelerator or platform-specific builds, several package managers with different incantations. A
page that holds one `pip install` command is a nav entry a reader has to click to learn nothing.
Whichever way you go, the nav must match the files on disk — a `start/install` entry pointing at
a file nobody wrote is the way this section rots first, and the three-page shape means every
entry here is cheap to check.

### It is not a fifth mode

Nothing in `start/` teaches a skill, walks through a task, specifies behaviour, or explains a
design at depth; it routes a stranger to the mode that will. It sits beside `about/` as the
other non-mode home: `about/` holds material that is not practitioner documentation, `start/`
holds the pages for a reader who is not yet in the four modes' audience. Four rules keep it from
drifting into a fifth mode, and they are the whole discipline of the section:

- **No page in `start/` is the canonical home for a fact.** Its tables name a call or an option
  and link to the reference row that owns it. The moment a default or a type is *defined* here,
  there are two authoritative copies and they will drift.
- **Two screens per page.** When `what-it-does.md` grows a passage on how the mechanism works,
  EXTRACT it to explanation. When `quickstart.md` grows a second scenario, a platform branch, or
  a troubleshooting section, it is turning into a tutorial or a how-to; move the growth, not the
  page.
- **Nothing in `start/` is a prerequisite.** A reader who ignores the whole section and opens the
  tutorial loses nothing. If a tutorial says "first read `what-it-does`", the tutorial has a gap.
- **Three pages, four with an earned install page, five with an earned `principles.md`, and no
  more.** Every page past the third is argued for in the summary. A `start/` with six pages in
  it is the "Advanced" overflow bucket under a friendlier name.

In the nav, `start/` comes first, above Tutorials, and the root landing page gets a card for it
alongside the four mode cards. It needs no section landing page of its own — `what-it-does.md` is
the doorway, so list the three pages directly in the nav and point the card at that first page.
If the landing page carries a "where to start" routing list, that list and `is-it-right.md` are
the same job done twice: keep the short version on the landing page and let it link through.

One honest outcome of trying to write `is-it-right.md` is discovering that you cannot — that
nobody can say in a table which data the software suits. That is worth reporting as a finding
about the software, not papering over with a page of prose.

## Section landing pages

Every section needs an index page, and its job is not to list its children — the nav already
does that. Its job is to tell a reader **whether they are in the right place**, in the
vocabulary of their situation rather than yours.

A good section index does four things:

1. **States what this section is for, in one sentence, in user terms.** Not "This section
   contains how-to guides" — say "Solutions to specific problems, for people who already have
   the system running."
2. **Points elsewhere when this is the wrong place.** "If you have never used X before, start
   with the tutorial instead." This single line prevents most misnavigation, and it is the
   cheapest quality improvement available in a doc set.
3. **Groups its contents meaningfully** when there are more than about seven — by task family
   for how-tos, by subsystem for reference, by theme for explanation. Tutorials get a sequence,
   because order matters there and nowhere else.
4. **Says what is missing.** A "Not yet written" list is required whenever the section contains
   pages you did not write, and it is worth having even when it does not. An honest "we have no
   guide for X yet" costs nothing and buys enormous credibility; a section that silently implies
   completeness it does not have costs you the reader's trust in the whole nav.

Card grids look good and work well here, but the words matter more than the layout. A plain
annotated list with a good orienting sentence beats a beautiful grid of bare titles.

The **root** index page has a different job: route a stranger to the right mode within a few
seconds. Four entries, each with a one-line description phrased as the reader's own situation
("I want to learn the basics", "I need to get something done", "I need to look something up",
"I want to understand how it works"), plus a fifth for the reader who has decided nothing yet
("I want to know what this is and whether it fits"). Add whatever the site's single most common
entry point is — usually install, or the tutorial.

## Navigation

- **Four top-level entries**, with the orientation doorway (`start/`) first and the
  non-practitioner home (`about/`) last. When something resists classification it is usually two
  things fused, not a fifth mode.
- **Two visible levels is usually right.** Section → page. A third level of nesting means a
  reader has to open two things to see whether the page they want exists.
- **Group lists longer than about seven.** Diátaxis notes that "lists longer than a few items
  are very hard for humans to read." A how-to section with forty guides needs task-family
  subgroups.
- **Sort by mode's own logic.** Tutorials in sequence (order is pedagogical). How-tos by
  frequency or task family rather than alphabetically, so the common cases surface first.
  Reference mirrors the product. Explanation from foundational to specialised.
- **Titles carry the mode.** How-tos begin "How to". Explanation reads with an implicit "About".
  Reference is a noun. If nav titles differ from page titles, keep them consistent in mode
  signalling.
- **Make the current mode visible** in the chrome — breadcrumbs, a highlighted section, a
  per-section sidebar. Most readers arrive mid-site from a search engine and need to know what
  kind of page they landed on.

## Naming the sections

The mode names are for authors; the section names are for readers. "Tutorials", "How-to guides"
and "Reference" are clear enough to use verbatim. "Explanation" is the one that reads oddly to
users — Diátaxis explicitly permits *Discussion*, *Background*, *Conceptual guides* or *Topics*.

What matters is that the name signals the *kind* of reading, not the subject. Names that fail
this test: "Guides" (which mode?), "Documentation" (all of it?), "Advanced" (a difficulty
level, not a mode — and reliably a dumping ground), "User Guide" (usually tutorial + how-to +
reference fused).

## Cross-linking discipline

Separation only works if delegation works. Each mode stays lean by pointing at the others, and
the link pattern is asymmetric by design:

| From | To | When |
| --- | --- | --- |
| Tutorial | Reference | At the end. "You used `search()`; here are all its options." |
| Tutorial | Explanation | At the end. "Curious why the client caches connections?" |
| How-to | Reference | Inline, wherever you deliberately did not enumerate options. |
| How-to | Explanation | In a "see also" at the end. |
| How-to | Tutorial | At the top, only as a prerequisite signpost. |
| Reference | Reference | Freely — related entries, glossary terms. |
| Reference | How-to | Sparingly, when a task is the obvious next question. |
| Explanation | everything | Freely. Connection is the mode's whole job. |

Rules that keep this from degrading:

- **Do not link out of the middle of a tutorial.** Every mid-lesson link is an invitation to
  leave and not come back.
- **One canonical home per concept, and one table row per fact.** When you are about to explain
  something a second time, link instead — repeated explanation is the leading indicator of a
  missing explanation page. The same holds for atomic facts: a value with a type and a default
  lives in exactly one reference table, and every other mention links to it. Reference↔reference
  duplication is the most damaging kind, because both copies look authoritative and they drift
  apart silently.
- **A glossary in reference, `term`-linked from everywhere.** This is the cheapest way to stop
  definitions duplicating across modes.
- **Prefer stable explicit anchors to heading-derived slugs** for cross-mode links. Heading text
  changes; explicit targets do not.
- **Fail the build on broken internal links.** Cross-linking is only load-bearing if it is
  enforced.

## Reference: generated and hand-written

Generated API docs are reference, but they are not all of reference. A complete reference
section usually contains:

- Generated API documentation (autodoc/autoapi/autodoc2, or the equivalent).
- CLI reference — commands, arguments, flags, exit codes.
- Configuration reference — every key, type, default, and constraint.
- Error and message reference, keyed by the exact text users will paste into a search engine.
- File format and schema reference.
- Environment variables, limits, compatibility and version matrices.
- Glossary.

Put generated output **inside** the reference section, not beside it:

```
reference/
  index.md          # cards/list covering all of the below
  cli.md
  configuration.md
  errors.md
  api/              # generated output lands here
```

The trap: most API-doc generators inject their own top-level nav entry by default, producing a
fifth section outside your four modes. Turn that off and place the generated index yourself.
The stack-specific setting is in `sphinx-myst.md`.

Docstrings are reference prose and inherit reference's constraints: describe, do not instruct,
do not explain, keep every entry of a kind the same shape. A docstring that teaches is a tutorial
hiding in the API.

## What is not practitioner documentation

SKILL.md lists the categories and says to give them an `about/` home. Three nuances that are not
obvious:

- **A version migration guide is genuinely a how-to guide** ("How to upgrade from 2.x to 3.0") and
  can live in either place. Pick one and be consistent.
- **Contributor documentation is a complete Diátaxis set of its own**, for a different
  practitioner. If it is substantial, give it its own four sections rather than mixing contributor
  how-tos into user how-tos.
- **An FAQ is almost always a symptom.** Each entry is a how-to, an explanation, or a reference
  fact that failed to get filed. Redistribute them and keep the FAQ only as a routing page of
  links — and if you do that, it must hold no answers of its own, or you have simply created a
  second home for the same facts.

## Two-dimensional doc sets

Documentation often has a second axis: multiple products, user roles (operator vs developer vs
end user), deployment targets (cloud vs self-hosted), or languages/SDKs. Diátaxis addresses
this directly and permissively — "Let documentation be complex if necessary."

Three shapes, and how to choose:

**Mode first, then dimension** (`how-to/kubernetes/…`, `how-to/docker/…`)
Choose when readers span the dimension — a single person deploys to both, and the mode is what
they are choosing between.

**Dimension first, then mode** (`self-hosted/how-to/…`, `cloud/how-to/…`)
Choose when readers are firmly on one side and rarely cross. Separate audiences get separate
doc sets that happen to share a domain.

**Mode first, dimension as tabs within a page**
Choose when the difference is a few commands, not a different task. One how-to with
per-platform tabs beats four near-identical how-tos, and keeps them from drifting apart.

The mistake is mixing shapes within one section. Pick per section if you must, but be explicit.

## Documenting a library or a scientific package

A library whose subject matter is itself technical — a solver, an inference package, a units
system, anything whose correct use depends on understanding what it computes — puts pressure on
two of the four modes that a web framework's docs never feel. The modes do not change. What
changes is how much structure explanation and reference need underneath them.

### Explanation usually wants two sections

"Why it is built this way" and "what the code actually computes" are two reading jobs. The first
serves a reader forming a mental model, who wants no formula and no code. The second serves a
reader who already has the model and wants to know exactly what runs: the model, the estimator,
the convergence criteria, the assumptions in one list. Fusing them produces the page everyone
bounces off — three friendly paragraphs, a derivation, three more friendly paragraphs.

Split the explanation mode into two sibling sections, `concepts/` and `how-it-works/` (or
`theory/`). Both are explanation and neither is a fifth mode; it is the same kind of split as a
how-to section that grows a subsection.

- **`concepts/` is read, and it is ordered.** Its landing page is a numbered reading sequence,
  each page building on the one before, because the ideas have dependencies even though the pages
  are not a tutorial. One mechanism per page, in words and pictures, and it asks the reader to
  run no code — code is the other two modes' job, and a concept page with a snippet in it is a
  tutorial that lost its nerve.
- **`how-it-works/` is consulted.** No reading order, every page standing alone, the symbols of
  the notation page throughout, and every threshold it mentions linked to the reference row that
  owns the value rather than restated beside the maths.

If you cannot say which of the two a page is, it is usually a concept page with a derivation
stapled to the end. EXTRACT the derivation.

### Reference holds more than the API

For this kind of project the reference inventory in the previous section grows four pages, and
each of them exists because some other page would otherwise own a fact it cannot keep.

**A glossary, with one word per meaning.** The project picks one term for each concept and uses
only that term, everywhere, including in docstrings. This is worth stating as a rule and not
just a page, because synonyms are how a doc set stops being searchable: a reader who greps for
the word the tutorial used finds nothing in the reference.

**A notation page, with one symbol per meaning**, when the docs carry mathematics. The table has
four columns — symbol, meaning, the name the code uses, and the page that defines it — and the
third column is the point of the page. A reader holding the paper's $\rho$ needs the attribute
to read it off, and a reader holding `result.samples` needs the symbol to follow the derivation.
Without this crosswalk the maths and the API are two vocabularies for one object and the reader
has to build the mapping themselves.

**A warnings-and-errors page, keyed by the exact message.** Group by exception or warning class,
one entry per message, and use the message text itself as the entry's term so it matches what
the reader pastes into a search engine. Declare once that run-time values appear in angle
brackets (`<n>`), then give each entry the same three fields:

```
`<the message, verbatim, truncated with … if long>`
: **When.** The call and the condition that produce it.
  **Cause.** What is actually wrong, in one or two sentences.
  **Fix.** What to change, naming the argument or constructor.
```

Thresholds named in the entries link to the defaults page instead of repeating the value. The
companion is a how-to that maps symptom to fix, and that how-to needs a second list for the
mistakes which bias a result *without* producing a message — those have no text to key on, so
nothing else in the doc set catches them, and they are usually the most expensive thing a reader
can get wrong.

**A defaults-and-constants page, generated from the code.** Named constants and thresholds have
exactly one home, and if that home is hand-written it drifts within two releases. Generate the
tables from the source between markers (`<!-- defaults:start -->`), with columns for the name,
the value, the module, and what it controls. Two rules keep it honest: per-parameter defaults
stay in the signature in the generated API reference and the page says so, rather than being
copied into a second table; and internal constants are listed, marked as explaining behaviour
rather than offering a setting, because a reader debugging a surprise needs them and will
otherwise read the source to find them.

### A field dimension, when several communities invented the same thing

Some software lands in communities that each derived its subject independently and named every
piece differently. The vocabulary problem is then not a glossary entry, it is the whole barrier
to entry: a reader recognises their own problem only in their own words, which are not yours.

The shape that works is a `fields/` section — the dimension-beside-the-modes case of
[Two-dimensional doc sets](#two-dimensional-doc-sets) — with one page per community and a
landing page carrying two tables:

- **the vocabulary crosswalk**, one row per community and one column per term of yours, with a
  dash where a community has no word for it. The dashes are informative; they tell a reader from
  that community that they are about to meet an idea their field does not name.
- **the methods table**, one row per community and one column per thing the software does,
  naming the method and the existing package that community already uses. A reader arriving from
  a field wants to know what this replaces before they want to know how it works.

Each community page then states the problem in that community's terms, maps it onto yours, and
lists only what the software adds *for that community*. The discipline that makes this survive:
**a community's own words appear only on its own page**, as synonyms, and every other page uses
the glossary's word. Otherwise the synonyms leak and the glossary stops being canonical.

These pages make claims about other people's software, which goes stale in a way your own API
reference does not. Say so on the page: the date the survey was made, and that releases of your
own project do not refresh it. That is a provenance note, not a verification claim, and it is
the honest alternative to a comparison table that silently ages.

### A package family is a dimension, not a section

When a project ships a core package plus satellites — optional backends, interop shims, a
testing-strategies package — the satellites do not get folded into the core's four sections. The
core's tutorials, how-tos, reference and explanation document the core. Each satellite keeps its
own docs tree in its own directory, and the site surfaces them as a separate nav group beside
the modes.

A satellite's tree is small and shaped like a doorway rather than a doc set: what it is, what it
depends on (often the interesting fact — a satellite that avoids the heavy dependency is why it
exists), how to install it, one at-a-glance example, and a list of its own pages, which are
whichever modes it genuinely needs. Most satellites need a how-to and a generated API page and
nothing else; a satellite with four mode folders and one page in each has four stubs.

Route to them from two places: the landing page's nav group, and the rows of `is-it-right.md`
whose answer lives in a satellite. A reader should never have to know the package family's
boundaries to find the page they need.

If the satellites live in one repository with the core, symlink each one's `docs/` into the
site's tree rather than copying it, so the satellite's docs stay next to the satellite's code
and there is one copy. Whatever you do, exclude the symlink targets' own build artifacts from
the site build.

### Design records get a home, and no citations

A project that works to a written spec accumulates design material — the spec, an
implementation plan, a landscape survey, a test plan. It is not practitioner documentation and
it is not `about/` material either, because `about/` is read by users and this is not. Give it
`design/` (or `about/design/`), say on its landing page that the pages record how the project
was designed and are exempt from the user-page rules, and leave it out of the four sections.

Then one rule, which is easy to break and hard to notice: **user pages and docstrings never cite
a design record.** No "see DECISIONS #14", no link to a plan from a how-to. The reason for a
design belongs in the issue or the pull request that made it, and in a comment beside the code;
a reader who follows a decision number out of a how-to lands in material written for a different
audience and dated differently. When a user page seems to need the reason, what it needs is an
explanation page.

### A how-to index can be the pipeline

When the product has one dominant workflow, the how-to landing page is that workflow, numbered,
each step naming the guide that covers it. The reader learns the shape of the whole job and
their place in it from the index, which is more than an alphabetical list of the same links can
do, and a guide that fits nowhere in the numbered steps is a guide to question.

## Scale

For large doc sets, Diátaxis's advice is to add layers rather than flatten: group into
subsections of around seven items, and let hierarchy grow where it is genuinely needed. The
structure should follow "how users actually perceive the product, not how creators designed
it."

Practical consequences at scale:

- The **how-to section grows fastest and is the first to need subgrouping**. Group by user task
  family, not by internal component.
- **Reference grows with the product** and should track the product's own structure, so it
  mostly organizes itself.
- **Tutorials should stay few.** A doc set with twenty tutorials has how-to guides mislabelled.
  A well-served product often needs two or three: a first-contact lesson and one or two deeper
  ones per major capability.
- **Explanation grows with the interesting decisions**, not with the feature count.

If a section is unmanageable even after grouping, that is often a signal the *product* has two
audiences, and the two-dimensional shapes above apply.

## Keeping it that way

A restructure decays back to the mess it came from within a year unless the discipline is
written down and enforced.

- **Put the compass in the contributing guide**, with the four-row table and a sentence on
  where each mode lives. Most contributors will follow a rule they can see.
- **Add a docs PR checklist**: which mode is this page, does the title signal it, does it link
  out rather than duplicate, does it avoid the neighbouring mode's job.
- **Enforce mechanically what can be**: strict builds, link checking, example execution in CI,
  and a lint on titles if you can manage it (how-tos start with "How to").
- **Use issue templates that name the mode** — "missing how-to", "reference gap", "unclear
  explanation" — so incoming requests arrive pre-classified.
- **Re-run the inventory scan periodically.** Rising mixedness scores are an early warning that
  pages are re-fusing.
